# TASK-02: AuthentikOAuthProvider kind (full OAuth2/OIDC provider)

## Ticket
- Ticket: none
- Status: Completed (e2e against real Authentik remains TASK-08)
- Milestone: parity-with-jeffresc-v0.2.5

## Context
JeffResc embeds the provider inside its application kind
(`AuthentikOAuth2Application.spec.provider`); this repo splits it into its own
kind (scope.md). Parity means every JeffResc provider field, plus the gaps that
break logins today.

**Known-broken upstream, fix here:** JeffResc issue #279 -- providers are created
with an empty `grant_types`; on Authentik 2026.8 every OIDC login fails with
"Invalid grant_type for provider". The spec has no grant-types field and the
client never calls `SetGrantTypes`.

## Implementation Plan
### Phase 1: spec (parity)
- [x] `authorizationFlow`, `invalidationFlow` -- required, by flow slug
      (plus optional `authenticationFlow`)
- [x] `redirectUris` -- list, min 1; each `{url, matchingMode: strict|regex, type:
      authorization|logout}`; custom schemes allowed (no URL pattern imposed)
- [x] `scopes` -- by `scope_name`; default `[openid, profile, email]`; managed
      mapping preferred on duplicates
- [x] `clientType` confidential|public (default confidential)
- [x] `accessCodeValidity` (default minutes=1), `accessTokenValidity` (minutes=5),
      `refreshTokenValidity` (days=30), optional `refreshTokenThreshold` --
      validated duration strings
- [x] `subMode` enum: hashed_user_id|user_id|user_uuid|user_username|user_email|user_upn
- [x] `includeClaimsInIdToken` (default true), `issuerMode` global|per_provider
      (default per_provider)
- [x] `propertyMappings` -- UUID **or** name
- [x] `signingKey` -- certificate by name (default "authentik Self-signed Certificate")
- [x] `clientId` -- optional; generated by Authentik when omitted, reported in
      `status.clientId`, never written back into spec.

### Phase 2: beyond parity
- [x] `grantTypes` -- explicit list, default (`authorization_code`,
      `refresh_token`), MinItems=1, always sent, so #279 cannot recur (real
      Authentik >= 2026.8 verification is TASK-08)
- [x] `encryptionKey`, logout URI + method (CEL: method requires URI)
- [ ] JWT federation sources/providers -- deferred; never touched by PATCH,
      so values set in the UI are preserved
- [x] Provider name is stable and explicit (`spec.name`, default metadata.name).
      Do NOT hardcode JeffResc's `<slug>-provider` convention -- but TASK-05
      adoption must be able to target that name for migration.

### Phase 3: status
- [x] `providerPk`, `clientId`, `observedGeneration`, `Ready` condition with
      reasons Synced / Conflict / ReferenceNotFound / ReferenceAmbiguous /
      InvalidSpec / AuthentikError / connection reasons; events
      Created / Updated / Deleted / ProviderMissing / Orphaned / DeletionFailed

### Behaviour notes
- Identity is `status.providerPk` **plus** `status.clientId`. Before any PATCH
  or DELETE the provider's client ID must match `status.clientId`; a pk that
  now names another provider (connection switched to another Authentik, DB
  restore, client ID changed in the UI) is a `Conflict` and is never modified
  or deleted.
- Client ID: `spec.clientId` if pinned, else derived `k8s-<metadata.uid>`
  (public, not a secret). Because only this resource sends that ID, a create
  whose outcome was lost (timeout, undecodable response, failed status write)
  is recovered on the next reconcile instead of becoming a Conflict.
- A pre-existing provider with the same name and any other client ID is a
  `Conflict`, never taken over (adoption: TASK-05).
- Drift is repaired with PATCH containing only differing fields. Every managed
  field has a default (incl. `refreshTokenThreshold: seconds=0`,
  `logoutMethod: backchannel`), so removing a field from spec resets it.
  Unmanaged fields (client secret, JWT federation) are untouched.
- The finalizer is added/removed with a metadata-only patch, so explicit empty
  lists (`scopes: []`) are not re-defaulted.
- A provider deleted out of band is recreated (new client secret) with a
  Warning event.
- Finalizer `authentik.io/finalizer` deletes only providers this resource
  created (client ID re-checked). If the connection's objects are gone at
  deletion time (namespace teardown deletes the token Secret first), the last
  client the operator built for that connection is used. Only with no cached
  client (operator restarted) is the provider orphaned, with a Warning event.
  Fixable problems (no default connection, Forbidden, Authentik down) block
  deletion and are reported in the Ready condition plus a `DeletionBlocked`
  event.
- Follow-up: an `AuthentikDeployment` finalizer that waits for dependent API
  objects would make teardown deletion survive operator restarts too.
- Known limitation: a leftover provider (orphaned, or from a deleted and
  re-created CR with a new UID) blocks a new CR of the same name with
  `Conflict` until TASK-05 adoption or manual cleanup.
- Fake Authentik for tests: `internal/authentik/fakeauthentik`.

## Technical Decisions
