# TASK-02: AuthentikOAuthProvider kind (full OAuth2/OIDC provider)

## Ticket
- Ticket: none (Navigator-only)
- Status: Planned
- Milestone: parity-with-jeffresc-v0.2.5

## Context
JeffResc embeds the provider inside its application kind
(`AuthentikOAuth2Application.spec.provider`); this repo splits it into its own
kind (scope.md). Parity means every JeffResc provider field, plus the gaps that
break logins today.

**Known-broken upstream, fix here:** JeffResc issue #279 -- providers are created
with an empty `grant_types`; on Authentik 2026.8 every OIDC login fails with
"Invalid grant_type for provider". The spec has no grant-types field and the
client never calls `SetGrantTypes`.

## Implementation Plan
### Phase 1: spec (parity)
- [ ] `authorizationFlow`, `invalidationFlow` -- required, by flow slug
- [ ] `redirectUris` -- list, min 1; each `{url, matchingMode: strict|regex}`
      (JeffResc sends strict only); allow custom URI schemes (`^[a-zA-Z][a-zA-Z0-9+.-]*:`)
- [ ] `scopes` -- by `scope_name`; default `[openid, profile, email]`
- [ ] `clientType` confidential|public (default confidential)
- [ ] `accessCodeValidity` (default minutes=1), `accessTokenValidity` (minutes=5),
      `refreshTokenValidity` (days=30) -- validated duration strings
- [ ] `subMode` enum: hashed_user_id|user_id|user_uuid|user_username|user_email|user_upn
- [ ] `includeClaimsInIdToken` (default true), `issuerMode` global|per_provider
      (default per_provider)
- [ ] `propertyMappings` -- UUID **or** name (JeffResc: UUID only for OAuth2)
- [ ] `signingKey` -- certificate by name (default "authentik Self-signed Certificate")
- [ ] `clientId` -- optional; generated by Authentik when omitted. Never write a
      generated ID/secret back into spec (upstream Rust defect).

### Phase 2: beyond parity
- [ ] `grantTypes` -- explicit list with a sane default
      (`authorization_code`, `refresh_token`) so #279 cannot recur; test against
      Authentik >= 2026.8
- [ ] `encryptionKey`, logout URI + method, JWT federation sources/providers
- [ ] Provider name is stable and explicit (`spec.name`, default metadata.name).
      Do NOT hardcode JeffResc's `<slug>-provider` convention -- but TASK-05
      adoption must be able to target that name for migration.

### Phase 3: status
- [ ] `providerPk`, `clientId`, `observedGeneration`, conditions (see TASK-06)
